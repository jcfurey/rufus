# ARM and NVIDIA Jetson media

## Extracted GRUB live ISOs

The desktop's **Linux live USB → FAT32 files** option and CLI `linux --mode extract`
support conventional Casper/Debian GRUB menus. Architecture detection reads the
kernel header, including ARM64 Image/EFI zboot and ARM32 zImage/EFI formats; it
does not infer the target from the host CPU or filename.

| Target | Firmware and layout | GRUB data package | Removable EFI loader |
| --- | --- | --- | --- |
| x86-64 | BIOS+UEFI on MBR by default, or UEFI/GPT | `grub-pc-bin` and/or `grub-efi-amd64-bin` | `BOOTX64.EFI` |
| 32-bit x86 | BIOS/MBR | `grub-pc-bin` | Not implemented |
| ARM64/AArch64 | UEFI/GPT | `grub-efi-arm64-bin` | `BOOTAA64.EFI` |
| 32-bit ARM | UEFI/GPT | `grub-efi-arm-bin` | `BOOTARM.EFI` |

All targets need `grub-common`, `xorriso`, `dosfstools`, and `mtools`. Persistence
also needs `e2fsprogs`. For cross-architecture creation, the target module data
must be available to `grub-mkimage`; the backend checks explicitly and names
missing packages. The source checkout also searches its local development tools.
Set `RUFUS_GRUB_MODULES=/path/to/unpacked/usr/lib/grub` to use target module data
unpacked from distribution packages without installing a foreign-architecture
package into the host OS. The directory contains `arm64-efi/`, `arm-efi/`, etc.
Every generated loader and its external modules use the same platform module
directory. The portable executable does not bundle host GRUB packages.

The application/package use native Python/GI on x86 or ARM hosts. Linux's
device-capacity ioctl is selected for the host's 32/64-bit ABI. The CI matrix
includes native amd64 and ARM64 build, unit, GUI, and applicable firmware tests;
remote ARM64 execution remains pending after this local development session.

UEFI loaders generated by extraction are unsigned and require Secure Boot off.
BIOS is refused for ARM. Explicit architecture mismatches fail before output or
device access. Extraction needs explicit kernel/initrd paths and conventional
menu entries; unsupported variables, directory/external links, mixed architectures, FAT name
collisions, and oversized files are refused. Conventional Syslinux/ISOLINUX
Casper/Debian menus can also be extracted as described below.
The generated menu retains live arguments, removes ISO-scan arguments, and
enables or disables persistence explicitly. Existing media-check manifests are
regenerated for the complete output tree.

```sh
./rufus-linux linux /path/to/arm64-live.iso --mode extract \
    --output /tmp/arm64.img --persistence-mib 1024
./rufus-linux linux /path/to/armhf-live.iso --mode extract \
    --architecture arm --output /tmp/arm32.img
./rufus-linux linux /path/to/x86-live.iso --mode extract \
    --firmware both --output /tmp/x86.img
```

Persistence defaults to zero for CLI extraction and 1024 MiB for hybrid mode.
Use the desktop checkbox or `--persistence-mib` to choose it. `--size-mib` controls
a new extracted output image's capacity; physical drives use their whole size.
The existing hybrid mode retains the source ISO's firmware and architecture.

## Syslinux/ISOLINUX live menus

FAT32 extraction accepts conventional Casper/Debian Syslinux menus using LABEL,
KERNEL/LINUX, APPEND, INITRD, and static INCLUDE/MENU INCLUDE directives. Includes
and relative boot paths resolve from the original configuration's working
directory, including safe parent paths within the ISO. Include depth/size,
cycles, missing files, duplicate labels, and default-entry compatibility are
checked. Global APPEND is inherited; a local APPEND replaces it, and `APPEND -`
clears it. Multiple initrds and an explicit INITRD override are supported.

`--bootloader auto` prefers an existing supported GRUB menu. Otherwise it parses
the Syslinux menu and uses native Syslinux for x86 BIOS plus matching GRUB for
x86-64 UEFI. ARM or UEFI-only extraction automatically uses GRUB. Explicit
`--bootloader syslinux` is rejected for ARM or UEFI-only output; `--bootloader
grub` can translate a Syslinux source without requiring a Syslinux installer.
An explicit Syslinux choice can also convert a supported GRUB-only source menu.
The same choices appear in the desktop's FAT32 settings.

Native BIOS installation requires the host's `syslinux` 6.x mtools installer
and `mtools`, and uses bundled upstream Rufus Syslinux MBR code. The installer
operates on a new temporary FAT32 file. Its installed `ldlinux.sys` banner and
embedded `ldlinux.c32` are checked against that exact installer. No ISO COM32
module is referenced by the generated menu, so an older source ISOLINUX release
does not need to share the host installer's ABI. Set `RUFUS_SYSLINUX` to a native
installer path if it is not on PATH. A foreign x86 installer cannot run directly
on an ARM host; use a native build or select GRUB.

The generated BIOS menu is a simple text prompt with labels/titles and a default
timeout; it retains compatible default selection and serial settings. Original
configurations remain in their source directories. Only supported live Linux
entries are converted. Omitted utility/chain labels are reported in CLI JSON;
an unsupported default is refused. Dynamic UI/default programs, password/menu
access controls, custom persistence stores, unknown boot directives, and quoted
Syslinux boot paths/arguments require hybrid/DD mode. Original menu graphics,
chain loaders, and interactive utility programs are not reproduced. This is
not a general Syslinux interpreter or an extraction path for every installer.

Both generated firmware menus use the same persistence choice and rewritten
ISO-scan arguments. Checksums include generated loader files after installation.
BIOS-only Syslinux output needs no GRUB data; UEFI still needs the target's GRUB
package. The existing ARM defaults, unsigned-loader limits, and complete vendor
board-image restoration remain applicable.

```sh
# Auto-detect the source menu; use native Syslinux BIOS and GRUB UEFI if needed.
./rufus-linux linux /path/to/syslinux-live.iso --mode extract \
    --output /tmp/syslinux-live.img --persistence-mib 1024

# BIOS-only output with the native Syslinux installer, without GRUB dependencies.
./rufus-linux linux /path/to/syslinux-live.iso --mode extract \
    --bootloader syslinux --firmware bios --output /tmp/syslinux-bios.img

# Translate a conventional Syslinux menu to GRUB for UEFI-only output.
./rufus-linux linux /path/to/syslinux-live.iso --mode extract \
    --bootloader grub --firmware uefi --output /tmp/grub-uefi.img
```

Run `tests/syslinux_smoke.py --kernel /path/to/x86-64/vmlinuz --output-dir
/tmp/new-syslinux-test` with a local static `/usr/bin/busybox` (or `--busybox`),
QEMU, SeaBIOS, OVMF, and extraction tools. It creates an ISO/menu fixture with
a real kernel and two initrd archives, then boots the generated FAT32 image
as USB media under BIOS and UEFI, using disposable QEMU snapshots. This validates
loader/kernel handoff and initrd composition. Separately, real DragonOS GRUB
menus converted to native Syslinux media passed Casper persistence write/reboot/
read tests under BIOS/Syslinux and UEFI/GRUB with a 256 MiB ext4 store in private
VM overlays. Additional Syslinux-source distributions and physical firmware
combinations remain acceptance work. Reproduce the Casper test with
`make -C linux live-test LIVE_ISO=/path/to/casper.iso LIVE_LAYOUT=extract
LIVE_BOOTLOADER=syslinux LIVE_OUTPUT=/tmp/new-casper-test`.

Debian Live 13.7.0 also passes real live-root write/reboot/read checks through
BIOS and UEFI in hybrid, extracted GRUB and extracted Syslinux layouts. Static
submenus may repeat omitted utility labels in separate scopes; repeated live
labels remain ambiguous and are refused. Root live defaults are retained.
Read-only extracted files are made writable only in the private workspace.
Internal links to regular files are copied; Debian's root `debian -> .` and
`dists/{stable,testing,unstable}` CD aliases are omitted and reported in CLI JSON.
Other directory, external, dangling and cyclic links remain unsupported.
See [PERSISTENCE.md](PERSISTENCE.md) for the test matrix and limits.

The supported directives follow the upstream
[Syslinux configuration reference](https://wiki.syslinux.org/wiki/index.php?title=SYSLINUX).

## Raspberry Pi and other board-specific images

Use **Disk image (DD)** or CLI `write` for the board vendor's complete IMG, ZIP,
or compressed image. The shared writer restores firmware, DTBs, partition
offsets, and root filesystems unchanged. Generic ARM UEFI extraction does not
install Raspberry Pi firmware or synthesize a board's boot layout. The vendor
image and firmware must match the board. File-backed tests check restoration
of a compressed multi-partition board fixture; they do not establish that a
particular Raspberry Pi or carrier board boots.

## NVIDIA Jetson workflows

The **NVIDIA Jetson** desktop mode and CLI `jetson` require a model, target
storage, and installation method. Choices cover Orin Nano, Orin NX, AGX Orin,
Thor, Xavier NX, AGX Xavier, Nano, TX2, and TX1. Model/storage/method combinations
that do not fit the supported reference profiles are blocked. Module SKU,
carrier revision, release compatibility, and third-party BSP selection remain
the user's and vendor installer's responsibility.

| Method | Rufus operation | Installation on the Jetson |
| --- | --- | --- |
| Installer USB (Orin/Thor) | Check NVIDIA overlay/repository and ARM64 EFI loader, then copy the complete hybrid ISO unchanged | NVIDIA's booted installer selects supported attached NVMe/eMMC/microSD/USB storage |
| Legacy SD image (Nano, Xavier NX, Orin Nano developer kits) | Decompress, write, and verify the exact developer-kit SD image | Boot that card with firmware compatible with its JetPack release |
| Direct BSP recovery (all listed families, subject to matching BSP workflow) | Review board profile, connected recovery USB identity, command and firmware scope; authorize one logged BSP job | NVIDIA flash.sh/initrd tools install OS/firmware without SDK Manager |
| Recovery setup (all listed families) | Inspect NVIDIA USB devices and open installed SDK Manager | NVIDIA's wizard detects the board and handles Force Recovery, authentication, QSPI/eMMC/NVMe flashing, and confirmation |

For current ISO structure and supported storage, see NVIDIA's
[flashing guide](https://docs.nvidia.com/jetson/archives/r39.2.1/DeveloperGuide/SD/FlashingSupport.html)
and [ISO customization reference](https://docs.nvidia.com/jetson/archives/r39.2.1/DeveloperGuide/SD/JetsonISOCustomization.html).
The ISO's vendor loader, packages, installer overlay, and target partition
selection are preserved. Generic Linux extraction/persistence modes refuse
Jetson installers. Validation can read the ARM64 loader from the embedded
`boot/grub/efi.img` when it is absent from the outer ISO filesystem.

The installer ISO belongs on a **host USB flash drive**, distinct from the
Jetson's target storage. The [Orin Nano setup guide](https://docs.nvidia.com/jetson/orin-nano-devkit/user-guide/latest/quick_start.html)
describes the firmware prerequisites. SD images do not update QSPI. Use the
matching legacy guide for [Nano](https://developer.nvidia.com/embedded/learn/get-started-jetson-nano-devkit),
[Xavier NX](https://developer.nvidia.com/embedded/learn/get-started-jetson-xavier-nx-devkit),
or [Orin Nano's older firmware path](https://docs.nvidia.com/jetson/orin-nano-devkit/user-guide/latest/update_firmware.html).

[SDK Manager](https://developer.nvidia.com/sdk-manager) is not bundled or
automatically installed. Recovery needs a host OS and CPU architecture supported
by the selected SDK Manager/JetPack release; legacy boards may need archived versions. A third-party
carrier needs its vendor's BSP/configuration. Rufus opens the installed wizard
without passwords, automatic EULA acceptance, flashing flags, or guessed board
IDs. `jetson-devices` reports NVIDIA USB descriptors and recognized recovery
families/connection identities. The BSP or SDK Manager performs authoritative
EEPROM/SKU detection.

```sh
# Read-only instructions and USB inspection.
./rufus-linux jetson --model agx-orin --storage emmc --plan
./rufus-linux jetson-devices

# NEW file-backed output; no physical drive or Jetson firmware is modified.
./rufus-linux jetson /path/to/jetsoninstaller-arm64.iso \
    --model orin-nano --storage nvme --output /tmp/jetson-usb.img
./rufus-linux jetson /path/to/jetson-nano-sd.zip --method sd \
    --model nano --storage sd --output /tmp/jetson-sd.img

# Open the installed recovery wizard. Rufus does not start flashing.
./rufus-linux jetson --model agx-orin --storage emmc --method recovery --launch-sdkmanager

# DESTRUCTIVE: host installer USB, separate from the Jetson's NVMe target.
./rufus-linux jetson /path/to/jetsoninstaller-arm64.iso \
    --model orin-nano --storage nvme --device /dev/sdX --confirm /dev/sdX
```

Use `--sha256` to check a published download checksum. Media are staged and
validated before requesting drive access; allow temporary space for the complete
decompressed image. Structural checks do not establish release authenticity,
vendor signatures, or board compatibility. Physical Jetson installations and
QSPI/eMMC/NVMe recovery flashes have not been performed. Current tests use
structural ISO fixtures, unchanged board-image round trips, and mocked wizard
launches, plus synthetic direct-BSP/helper jobs and actual R39.2.1 offline BSP
inspection/planning. See [JETSON_RECOVERY.md](JETSON_RECOVERY.md) for direct
recovery commands, BSP/host prerequisites, storage scope, and limitations.
ARM UEFI kernel tests are separate and do not emulate Jetson hardware.

## Reproducing ARM firmware validation

`tests/arm_smoke.py` boots a real kernel through an extracted FAT32 USB image and
matching GRUB. Supply a Linux kernel, static BusyBox, and AAVMF/AAVMF32 firmware
locally; the test performs no downloads and uses no physical devices:

```sh
python3 linux/tests/arm_smoke.py --architecture arm64 \
    --kernel /path/to/arm64/vmlinuz --busybox /path/to/arm64/busybox \
    --firmware-code /usr/share/AAVMF/AAVMF_CODE.fd \
    --firmware-vars /usr/share/AAVMF/AAVMF_VARS.fd \
    --output-dir /tmp/new-arm64-boot-test
```

For ARM32, use `--architecture arm`, an ARM32 kernel/BusyBox, and
`AAVMF32_CODE.fd`/`AAVMF32_VARS.fd`. Output directories must be new. These tests
establish firmware-to-kernel handoff. The separate
[ARM live-root tests](ARM_LIVE_TESTS.md) now pass Casper write/reboot/read and
disabled-persistence controls on ARM32 and ARM64 through UEFI USB boot. They use
locally assembled Ubuntu Base/Casper fixtures and stop before user customization.
ARM userspace sessions, native ARM host CI and board-specific compatibility
remain separate acceptance work.
